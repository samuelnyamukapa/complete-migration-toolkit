# Recipes and gates make cmtk data trustworthy

cmtk can be very good at producing missing test data and test artefacts, but only if `/cmtk:data` is built as a schema-reading **recipe compiler with mechanical gates** rather than an LLM that writes rows. The evidence is consistent: un-guided LLM inputs are invalid **25–75% of the time** (DiffSpec's best configuration still produced 31% invalid tests; a base Llama3-8B produced semantically valid REST parameter values only ~23–25% of the time), while every strong result — Meta's 73% reviewer acceptance, American Express's 166/166 parity on a 4,114-line production program — pairs a proposing model with a deterministic oracle it cannot fool. Structure-derived data (valid, boundary and negative values from OpenAPI, JSON Schema, DDL, copybooks; FK-consistent seeds; byte- or content-stable CSV/xlsx/PDF/docx fixtures) is a solved engineering problem with permissively licensed Node parts, and cmtk's parity-first premise solves the one problem that defeats generic generators — the expected output — because the legacy system is the derived oracle. No existing tool does the whole job for a Node 22 toolkit serving .NET/SQL Server migrations: schema-derived negative and boundary generation lives only in Python's Schemathesis, SQL Server subsetting only in Java's Jailer, no maintained XSD-to-instance generator exists for Node, and the MCP/skill market is Faker wrappers plus seeders that charge for determinism. Because the 2025–2026 data shows verification is now the bottleneck (experienced developers 19% slower with AI, only 33% trusting its output, 66% frustrated by "almost right" code), the design should optimise every choice for how fast a tester can trust a generated set: a reviewable recipe, every row traceable to a technique and coverage item, oracle tags per field, a provenance manifest, mandatory negative and boundary quotas, and a gate that rejects anything that fails schema validation, replay stability or coverage delta.

## Review capacity, not generation speed, is the constraint cmtk must respect

Sam's own framing — development is fast, testers are struggling — is what the strongest 2025–2026 studies measure. METR's randomised trial of 16 experienced developers on mature repositories (~10 years old, >1M lines) found they took **19% longer** with AI tools while believing they were 20% faster, accepted **fewer than 44%** of generations, and found that "even accepted suggestions often required substantial review and editing" ([DX summary of METR](https://getdx.com/blog/metr-study-on-how-ai-affects-developer-productivity/)). Stack Overflow's 2025 survey of more than 49,000 developers found **84% adoption but only 33% trust** in AI accuracy (down from 43%), with **66%** naming "almost right, but not quite" solutions as the top frustration and **45%** saying debugging AI code takes longer than expected ([VentureBeat](https://venturebeat.com/ai/stack-overflow-data-reveals-the-hidden-productivity-tax-of-almost-right-ai-code)). DORA's 2025 report warns that downstream bottlenecks "neutralize any gains from AI" and that nearly half of teams operate ineffectively on at least one axis such as missing automated tests or manual-only QA ([Swarmia on DORA 2025](https://swarmia.com/blog/dora-2025-report-ai-readiness)); telemetry summarised by Stavros shows review time rising 91% while lead time and change-failure rate did not improve, and his conclusion is the one cmtk should internalise: "a rollout that funds generation and not verification is buying a bigger tap for a pipe you have not touched" ([Stavros](https://thinkpieces.stavros.io/posts/the-bottleneck-ai-coding-assistants-moved-rather-than-remove/)).

The specific failure shape to design against is plausible-but-wrong data, which costs more review time than obviously wrong data. The automation research Stavros cites finds people catch about a third of errors when automation is usually right versus three quarters when it visibly fails sometimes ([Stavros](https://thinkpieces.stavros.io/posts/the-bottleneck-ai-coding-assistants-moved-rather-than-remove/)). James Bach reports a **57% failure rate across 4,080 attempts** at simple test-data generation, JSON-to-SQL outputs whose column types and lengths changed between runs, and a fabricated summary; his rule, "Never treat a pleasing demo as evidence of trustworthy behaviour", came from a vendor demo that took 30–40 hours to review ([Bolton & Bach, Oct 2025](https://developsense.com/presentations/2025-10-WhatAreWeThinkingInTheAgeOfAI-Ljubljana.pdf)). The MutGen paper gives the sharpest example of why coverage is a false comfort: LLM-generated tests reached **100% line and branch coverage with a 4% mutation score**, having tested day=0 and day≥2 but never day=1, the single value that distinguishes `<` from `<=` ([MutGen, arXiv 2506.02954](https://arxiv.org/html/2506.02954v6)). Thoughtworks put "complacency with AI-generated code" on Hold and moved fuzz testing to Adopt specifically because of AI-generated code ([Thoughtworks Radar vol. 32](https://thoughtworks.com/content/dam/thoughtworks/documents/radar/2025/04/tr_technology_radar_vol_32_en.pdf)).

The practitioner consensus on where to spend human effort points directly at a tool like `/cmtk:data`. Kief Morris on Fowler's site describes "on the loop" engineering, where developers build "test frameworks, constraints, and evaluation pipelines rather than inspecting every generated line" ([InfoQ](https://infoq.com/news/2026/03/mf-aiassisted-dev)); Kent Beck used a fixed test suite as the specification across a Rust→Python→Rust rewrite and watched for the agent "disabling or deleting existing tests" ([Beck via Signals](https://signals.aktagon.com/articles/2025/09/augmented-coding-beyond-the-vibes/)). For test data this means humans review the *generation rules and oracles*, not the rows, so the recipe must be a first-class, inspectable artefact and the rows must be derivable from it on demand. Everything that follows is judged by one question: how many minutes does a tester need before they trust this set?

## Experienced testers derive data by technique, source and oracle, not by column

A naïve generator enumerates columns and fills them; an experienced tester models variables, partitions them, picks boundaries, combines them under constraints, and names the oracle that will judge each result. The standard codifies this as a chain: ISO/IEC/IEEE 29119-4 (edition 2, 2021) defines ten specification-based techniques — equivalence partitioning, classification tree, boundary value analysis, syntax testing, combinatorial, decision table, cause-effect graphing, state transition, scenario and random — seven structure-based ones and error guessing, and every technique produces test conditions, then coverage items, then test cases, with a coverage measure defined for each ([ISO](https://www.iso.org/standard/79430.html); [ANSI preview](https://webstore.ansi.org/preview-pages/ISO/preview_ISO+IEC+IEEE+29119-4-2015.pdf)). That chain is the traceability model cmtk should adopt: a reviewer must be able to ask of any row "which technique and coverage item justify you, and what would be uncovered if you were deleted?"

The details of each technique dictate data values, not just counts. ISTQB's Foundation 4.0 syllabus requires partitions to be non-overlapping and non-empty with both valid and invalid partitions covered; its 3-value BVA example shows that for `if (x ≤ 10)` mis-implemented as `if (x = 10)`, testing 9 catches the defect while 10 and 11 do not, so cmtk should default to 3-value rather than 2-value BVA; state-transition testing at the "all transitions" level attempts each invalid transition one per test case "to avoid fault masking"; and decision-table rule counts grow exponentially, so the minimisation rule must be explicit rather than silent ([ASTQB study guide](https://study.astqb.org/?p=22)). NIST's empirical finding that **70–95% of failures involve only two interacting variables and practically 100% no more than six** — 34 on/off switches need ~17 billion exhaustive tests but 33 tests for all 3-way interactions and 522 for all 6-way — makes constraint-aware pairwise the default combination strategy, escalating to 3–6-way for high-risk parameter sets ([NIST](https://www.nist.gov/news-events/news/2010/11/Updated-nist-software-uses-combination-testing-catch-bugs-fast-and-easy)). Kaner, Padmanabhan and Hoffman add the deepest point: domain testing models "notional variables" that exist in the tester's model but "probably do not exist in the code" — age at booking derived from two dates, for instance — because "the tests come from the tester's mental model, not directly from the code" ([Kaner](https://kaner.com/?p=363)). A schema-only reading misses exactly the variables testers partition, which is why `/cmtk:data` must let the model (and the human) declare notional variables over the raw fields.

Testers also read the system through more than its schema. Whittaker's tours translate directly into generator strategies: the Intellectual and Antisocial tours give hostile and extreme values, the FedEx tour follows data through store-modify-lose cycles including Cyrillic and right-to-left character sets, the Obsessive-Compulsive tour repeats an action for idempotence, the Rained-Out tour cancels midway to leave partial-transaction states, and the Couch Potato tour submits defaults only ([Whittaker's tours summarised](https://www.softwaretestinghelp.com/?p=22928)). TMap's test-data lifecycle explains why provenance matters: reused data gives "inadequate coverage" and "timestamp and date fields age", masking must keep values valid (fictional bank account numbers that still pass checksums), subsetting speeds CI but performance tests still need full-size masked data, and the industry trend is "toward masking, subsetting, and synthetic data, and away from production data" ([TMap](https://www.tmap.net/node/426)). From these, cmtk should read four inputs in a declared trust order — schema, constraints and code first (types, lengths, nullability, FKs, check constraints, enums, state machines); requirements and acceptance criteria second (the only source that can expose defects of omission, which ISTQB notes white-box data "may miss"); masked production shape third (distributions, real max lengths, character sets, date ranges, outliers); and history fourth (prior versions and prior defects, Whittaker's Bad-Neighbourhood and Museum tours) — and tag each value with the source that justified it.

The oracle is where generated data most often fails silently, and the tester's literature is explicit that oracles are heuristic. Bolton defines an oracle as "a heuristic principle or mechanism by which someone recognizes a problem", notes that oracles can conflict and that claims in documents "can themselves be wrong", and lists the HICCUPPS consistency heuristics (History, Image, Comparable products, Claims, Users' expectations, Product, Purpose, Standards, Statutes, plus Familiarity) ([Bolton, Oracles](https://developsense.com/resource/Oracles.pdf)). Barr, Harman, McMinn, Shahbaz and Yoo's survey classifies oracles as specified, derived (previous execution results, earlier versions — the backbone of regression and migration testing), implicit (crash or 500 = problem) or human (judging whether inputs and outputs are "realistic and representative") ([Barr et al. summarised](https://en.wikipedia.org/wiki/Test_oracle)). Every expected value cmtk emits should carry its oracle class, and rows whose only oracle is human must be routed to review rather than auto-asserted. Finally, Meszaros's test smells describe exactly what testers distrust in bulk generated fixtures: the Mystery Guest, where "the reader can't see the cause-and-effect link between setup and verification"; Irrelevant Information, where tests fill "all the parameters with values whether or not they are relevant"; and the General Fixture shared by everything, which produces tests that "pass in one environment but not another" ([thoughtbot](https://thoughtbot.com/blog/mystery-guest); [8th Light](https://8thlight.com/insights/essential-amp-relevant-a-unit-test-balancing-act)). A trusted generator emits fresh, minimal, per-test data with role-based names and parameterised builders — `valid_user(last_name: "Doe")` — not one seed database named by incident.

Migration adds its own data strategy, and it is the strategy cmtk exists for. Reconciliation practice treats row counts as "the minimum, not a sufficient test", compares SUM/MIN/MAX/AVG for every numeric column to catch truncation and precision loss, checks every source primary key exists in the target and every foreign key resolves, flags string max lengths against target widths, and seeds deliberate edge cases: NULL versus empty string versus default, Latin-1→UTF-8, UTC→local and DST transitions, DD/MM versus MM/DD, DECIMAL→FLOAT altering currency, and VARCHAR(500)→VARCHAR(255) silent truncation ([Xylity](https://xylitytech.com/data-engineering/data-migration-testing-validation-reconciliation/)). The same source recommends **50–100 golden records per entity** — typical, edge, high-value and complex-relationship, verified by business users — and investigating "any discrepancy in financial totals, even $0.01". Zalando's Parallel Run shows the parity side: the monolith stayed the source of truth and mirrored every request to the new service's `/consistency-checks` endpoint, results were classed Matched/Unmatched/Failed, "comparisons do not require a 100% match", each endpoint had its own consistency target, scope was limited to calls "where idempotency can be guaranteed", and hidden monolith bugs surfaced during comparison ([Zalando](https://engineering.zalando.com/posts/2021/11/parallel-run.html)). Thoughtworks' legacy-displacement patterns name Feature Parity as "a key factor in several failed programmes" because defining the "as is" led to big-bang cutovers ([martinfowler.com](https://martinfowler.com/articles/patterns-legacy-displacement/)) — so cmtk's parity data must be scoped per seam and per endpoint, with discrepancy classifications (new defect, legacy bug preserved, legacy bug fixed, non-comparable field) stored as data.

## The tool landscape offers strong parts but no whole for Node plus .NET

For JSON Schema and OpenAPI, the in-process Node options are solid for valid data and absent for negative data. json-schema-faker 0.6.3 (published 2026-08-01, MIT, zero dependencies) is a TypeScript rewrite supporting JSON Schema 2019-09 and 2020-12 with a seedable Mulberry32 PRNG, AST-based `pattern` generation, `$ref` cycle detection and faker/chance extensions ([npm registry](https://registry.npmjs.org/json-schema-faker); [README](https://unpkg.com/json-schema-faker@0.6.2/README.md)); @faker-js/faker 10.6.0 is seedable but warns "you may get different values for the same seed" after upgrades and that date methods depend on the current date unless `refDate` is set ([fakerjs.dev](https://fakerjs.dev/guide/usage)); fast-check 4.10.2 adds shrinking and seed-plus-path replay to the minimal counterexample, but its only JSON Schema bridge, json-schema-fast-check, was archived in October 2022 ([fast-check Tips](https://github.com/dubzzz/fast-check/blob/68a4c78741d23f068febe8b2816474726133882c/documentation/1-Guides/Tips.md); [GitHub](https://github.com/unmock/json-schema-fast-check)). Mock servers do not change the picture: Prism 5.16.0 now requires **Node >=24.18**, says it is "not yet intended for programmatic mocking within test suites", and in dynamic mode generates random values by type ([npm registry](https://registry.npmjs.org/@stoplight/prism-cli); [Prism docs](https://docsearch.algolia.com/mcp/docs/repo/stoplightio/prism)); Mockoon wraps Faker helpers with seedable settings ([Mockoon docs](https://mockoon.com/docs/latest/templating/fakerjs-helpers/)); Dredd has not published since November 2021 ([npm registry](https://registry.npmjs.org/dredd)).

The most capable schema-driven generator is Python-only. Schemathesis 4.32.4 (MIT, Python >=3.11) runs four phases — examples, a coverage phase that emits boundary values per constraint (`minLength: 2, maxLength: 10` yields lengths 1, 2, 3, 9, 10, 11), fuzzing within constraints plus Hypothesis "interesting" values, and stateful testing from OpenAPI links and learned `Location` headers — and a negative mode that mutates the schema (for `minLength: 3` it sends `42`, `[]`, `""`, `"ab"`), with `seed`, `generation.deterministic`, unexpected-method probing, and JUnit/VCR/HAR/HTML exports plus cURL reproductions ([Schemathesis data generation](https://schemathesis.readthedocs.io/en/stable/explanations/data-generation/); [configuration](https://schemathesis.readthedocs.io/en/latest/reference/configuration/); [PyPI](https://pypi.org/pypi/schemathesis/json)). RESTler (MIT, Python plus .NET) infers producer-consumer sequences and gives deterministic per-bug replay logs, but its Docker agent image was last updated more than two years ago ([restler-fuzzer README](https://github.com/aharpervc/restler-fuzzer); [Docker Hub](https://hub.docker.com/r/microsoft/restapifuzztesting-restler-agent)). EvoMaster 6.2.0 (LGPL-3.0, released 2026-09-15) is "the only open-source fuzzer for Web APIs that supports white-box testing", but white-box is JVM-only — "JavaScript/TypeScript and C# white-box support was dropped" and .NET support is "an academic proof-of-concept" ([EvoMaster GitHub](https://github.com/WebFuzzing/EvoMaster); [Springer tool report](https://link.springer.com/10.1007/s10515-024-00478-1); [Maven Central](https://repo1.maven.org/maven2/org/evomaster/evomaster-client-java-controller/)). Independent benchmarks calibrate expectations: across 19 APIs no black-box tool exceeded **60% line coverage** in an hour (EvoMaster 56.8%, Schemathesis 54.5%), and spec-implementation mismatch appears in "almost 99%" of more than 1,000 public specs, with most rejected requests caused by domain-specific values the schema does not express and dependencies it does not declare ([Zhang & Arcuri](https://arxiv.org/pdf/2205.05325); [Kim et al.](https://arxiv.org/pdf/2204.08348)). Tcases (MIT, Java) is the one combinatorial generator that "produces invalid values as well as valid ones" from an OpenAPI definition ([Tcases](https://github.com/Cornutum/tcases)).

XML, WSDL and binary contracts are the weakest area, which matters for .NET Framework estates. Apache XMLBeans' `xsd2inst` emits placeholder text such as `string` and `id="3"` ([XMLBeans Tools](https://xmlbeans.apache.org/guide/Tools.html)); SoapUI Open Source 5.9.0 is EUPL-licensed and its sample values historically ignored `xs:pattern`, producing Latin filler for a `\+\d+-\d+` restriction ([Wikipedia](https://en.wikipedia.org/wiki/SoapUI); [SmartBear community](https://community.smartbear.com/discussions/soapui_os/generate-request-examples-with-xsd-restrictions/29916)); Oxygen's commercial generator documents that "Random can produce invalid values when a regexp restriction is involved" and has no seed ([Oxygen docs](https://www.oxygenxml.com/doc/ug-editor/topics/xml-schema-instance-generator.html)). The research found no maintained Node XSD-to-instance generator and only a toy npm protobuf fuzzer on a deprecated API, versus Go's seedable `protorand` ([pkg.go.dev](https://pkg.go.dev/github.com/sryoya/protorand)). The pragmatic route for cmtk is to translate XSD into a JSON Schema model and reuse json-schema-faker's string, pattern and format engines, serialising to XML — an approach, not a found tool.

Database-side generation splits by ecosystem and licence. In Node, drizzle-seed 0.3.1 (Apache-2.0, last release January 2025) is deterministic by seed but requires Drizzle table definitions and "can't reliably infer references, especially with circular dependencies" ([Drizzle docs](https://orm.drizzle.team/docs/seed-overview); [npm registry](https://registry.npmjs.org/drizzle-seed)); @snaplet/seed introspects a live database and is "fully deterministic" via copycat, but is FSL-1.1-MIT licensed, last published July 2024, and "receives only occasional fixes" after Snaplet wound down in 2024 ([npm registry](https://registry.npmjs.org/@snaplet/seed); [Supabase docs](https://supabase.com/docs/guides/local-development/seeding-your-database.md)). For subsetting real data, Jailer (Apache-2.0, Java) is the only open-source subsetter with documented dedicated **SQL Server** support; it extracts "referentially intact" slices as topologically sorted SQL, JSON, YAML, XML or DbUnit, breaking cycles by deferring nullable FK inserts ([Jailer README](https://cdn.jsdelivr.net/gh/wisser/jailer@master/README.md)). Greenmask (Apache-2.0, Go) adds virtual and polymorphic references and a deterministic SHA3 hash engine but is Postgres-first with MySQL in beta ([Greenmask](https://github.com/GreenmaskIO/greenmask); [release notes](https://www.postgresql.org/about/news/greenmask-020-025-releases-2974)). Commercially, Redgate Test Data Manager has a subsetting CLI with `startingTables` plus filter and manual relationships ([Redgate docs](https://documentation.red-gate.com/tdm/command-line-interface-cli/subsetting)), Synthesized TDK supports MSSQL with a free tier of 20 tables and 100k rows per table ([Synthesized docs](https://docs.synthesized.io/tdk/v1.65)), and Tonic Structural prices by source-data size with patented multi-database subsetting ([Tonic pricing](https://www.tonic.ai/pricing)). The market has consolidated and some open-source options have closed: SDV moved to BUSL-1.1 ([PyPI](https://pypi.org/project/sdv/1.37.3/)), Neosync's README says it is "no longer actively maintained" after its September 2025 acquisition ([Neosync README](https://cdn.jsdelivr.net/gh/nucleuscloud/neosync@main/README.md)), Gretel was absorbed into NVIDIA ([TechCrunch](https://techcrunch.com/2025/03/19/nvidia-reportedly-acquires-synthetic-data-startup-gretel)), and Delphix became Perforce ([SD Times](https://sdtimes.com/delphix/perforce-acquires-test-data-management-platform-provider-delphix)); the bright spot is MOSTLY AI's Synthetic Data SDK under Apache-2.0, which guarantees referential integrity between subject and linked tables via a context foreign key and lists a SQL Server connector ([MOSTLY AI](https://mostly.ai/blog/unlocking-ai-training-data-for-all-mostly-ai-releases-worlds-first-industry-grade-open-source-toolkit-for-synthetic-data); [docs](https://mostly.ai/docs/generators/tabular-synthetic-data)).

On the .NET side, the generators are mature but schema-blind. Bogus 35.6.5 (286.7M downloads) targets .NET Framework 4.0 and .NET Standard 2.0, so one generator library runs in both a Framework and a .NET 8 process; its docs recommend `Faker<T>.UseSeed(int)` over the global `Randomizer.Seed`, which has "rippling effects" where adding a rule shifts all later data, and its release notes warn that "deterministic sequences may have changed" after dataset changes ([NuGet](https://www.nuget.org/packages/Bogus/); [Bogus docs](https://docsearch.algolia.com/mcp/docs/repo/bchavez/bogus); [NuGet 21.0.4 notes](https://www.nuget.org/packages/Bogus/21.0.4)). AutoFixture 5.0.0-rc.1 (July 2026, MIT) targets net8.0 and .NET Framework 4.6.2 ([nubrowse](https://nubrowse.com/packages/AutoFixture/5.0.0-rc.1)). EF Core's `UseSeeding` runs only through `Migrate`/`EnsureCreated`/bundles and never when SQL scripts run externally, while `HasData` requires explicit keys, bloats migration snapshots and is "not recommended" for temporary test data ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/modeling/data-seeding)); neither can be the parity seeding mechanism because neither runs on the legacy side. Testcontainers.MsSql starts a real SQL Server container and runs ad hoc SQL through `ExecScriptAsync` ([Testcontainers .NET](https://dotnet.testcontainers.org/modules/mssql)), and BACPAC exports "are not transaction-aware", so snapshots must come from a quiesced copy ([Microsoft archive](https://learn.microsoft.com/en-us/archive/blogs/tip_of_the_day/sql-tip-of-the-day-bacpac-and-data-inconsistency)).

Document and file fixtures are well covered by permissive Node libraries, with three traps. The npm `xlsx` package is frozen at 0.18.5 (2022) with an unpatched High-severity prototype-pollution CVE on the read path — "a non-vulnerable version cannot be found via npm" — so reading untrusted workbooks should use exceljs 4.4.0 or the `@e965/xlsx` mirror ([OSV](https://osv.dev/vulnerability/CVE-2023-30533); [npm registry](https://registry.npmjs.org/@e965/xlsx)). Byte-identical output is not the default for any xlsx/docx/pdf writer because they embed "now": ExcelJS sets `created = new Date()`, JSZip entries default to the current date, pdfkit's file /ID is an MD5 of `CreationDate` plus the info dictionary, and pdf-lib's `updateMetadata` writes `ModificationDate = new Date()` — each has a documented hook to pin ([exceljs workbook.js](https://raw.githubusercontent.com/exceljs/exceljs/master/lib/doc/workbook.js); [JSZip docs](https://raw.githubusercontent.com/Stuk/jszip/main/documentation/api_jszip/file_data.md); [pdfkit security.js](https://raw.githubusercontent.com/foliojs/pdfkit/master/lib/security.js); [pdf-lib PDFDocument.ts](https://raw.githubusercontent.com/Hopding/pdf-lib/master/src/api/PDFDocument.ts)). Excel dates carry 1900/1904 epoch and timezone-conversion drift ([SheetJS issue #1565](https://git.sheetjs.com/sheetjs/sheetjs/issues/1565)), CSV delimiters follow the Windows list separator (semicolon in most European locales) unless a `sep=` line forces them ([Ablebits](https://ablebits.com/office-addins-blog/change-excel-csv-delimiter)), and cells beginning `=`, `+`, `-`, `@`, tab, CR or LF are formula-initiating ([OWASP CSV Injection](https://raw.githubusercontent.com/OWASP/www-community/master/pages/attacks/CSV_Injection.md)). For mainframe inputs, copybook-ts 0.2.0 (MIT, no runtime dependencies) parses copybooks and both decodes and encodes fixed-width, COMP-3 and cp037 EBCDIC records, returns money as strings because `PIC S9(16)V99` exceeds `Number.MAX_SAFE_INTEGER`, and refuses `REDEFINES` ([copybook-ts README](https://raw.githubusercontent.com/daopapp/copybook-ts/main/README.md)); AWS CardDemo supplies Apache-2.0 copybooks and sample EBCDIC datasets ([CardDemo](https://raw.githubusercontent.com/aws-samples/aws-mainframe-modernization-carddemo/main/README.md)). EDI is parse-only in Node — x12-parser streams segments, `edifact` validates but "writing/constructing messages is not supported" ([x12-parser](https://registry.npmjs.org/x12-parser); [edifact README](https://cdn.jsdelivr.net/npm/edifact@1.2.12/README.md)). For comparison, daff diffs tables by key with `--id`, `--unordered` and HTML rendering ([daff README](https://cdn.jsdelivr.net/npm/daff@1.4.2/README.md)), ExcelCompare shows the right knobs — `--diff_numeric_precision` and formula-versus-value — ([ExcelCompare](https://raw.githubusercontent.com/na-ka-na/ExcelCompare/master/README.md)), and Verify (.NET) is the fullest model of document snapshotting: newline normalisation, counter-based `DateTime_1`/`Guid_1` scrubbing with engine-defined ordering, and PDFs verified as an info file plus text per page, xlsx as CSV per sheet ([Verify scrubbers](https://raw.githubusercontent.com/VerifyTests/Verify/main/docs/scrubbers.md); [Verify dates](https://raw.githubusercontent.com/VerifyTests/Verify/main/docs/dates.md); [Verify.PdfPig](https://raw.githubusercontent.com/VerifyTests/Verify.PdfPig/main/readme.md); [Verify.ClosedXml](https://raw.githubusercontent.com/VerifyTests/Verify.ClosedXml/main/readme.md)). No JavaScript library implementing Verify-style counter scrubbing was found.

The AI-native layer — skills, plugins, MCP servers, products — is where the gap is widest. The research found no Anthropic-maintained test-data plugin: Anthropic's own docs say most of the official marketplace comes from partners and other authors, with Anthropic maintaining a smaller set such as commit-commands, code-review, feature-dev and the language servers, and the anthropics/skills repository's only testing skill is Playwright-driven web app testing, with its document skills "source-available, not open source" and described as unmaintained snapshots ([Anthropic marketplaces](https://code.claude.com/docs/en/plugins/anthropic-marketplaces.md); [SourcePulse mirror](https://www.sourcepulse.org/projects/16949073)). awesome-copilot's testing artefacts centre on Playwright test generation from a live app ([awesome-copilot mirror](https://git.cynarski.dev/Awesome/awesome-copilot/src/commit/0dcb9e9c220c613c246e486bd7bccb40fc19fd6e/prompts/playwright-generate-test.prompt.md); [playwright.dev](https://playwright.dev/agents/playwright-mcp-generating-tests)). Community skills are prompt guidance, not tooling: the best, h4vzz's `database-seeding`, prescribes inspecting constraints and FKs, computing parent-before-child order, choosing between "fixed-seed deterministic data, faker-generated data, or anonymized production snapshots", writing re-runnable transactional seed scripts, and verifying row counts and FK integrity — a reusable procedure with no code behind it ([skills.sh](https://www.skills.sh/h4vzz/awesome-ai-agent-skills/database-seeding); [fixture-generator](https://playbooks.com/skills/jeremylongshore/claude-code-plugins-plus-skills/fixture-generator)). MCP registries are crowded with Faker wrappers of negligible adoption and no stated seeding ([faker-mcp-server-docker](https://github.com/data-mindset/faker-mcp-server-docker)); the two schema-aware seeders are seedweaver-mcp, which reads DDL and emits FK-consistent inserts but puts **deterministic seeds, CSV output and CI use behind a $19/month licence** ([Socket.dev](https://socket.dev/npm/package/seedweaver-mcp)), and Seedfast, a Postgres-only closed engine requiring an API key ([mcpservers.org](https://mcpservers.org/servers/seedfast-ai/seedfast-mcp)). MockServer's built-in MCP endpoint can capture real traffic and promote it to mocks ([MockServer](https://www.mock-server.com/mock_server/ai_mcp_setup.html)). Products generate tests more than data: Copilot's `/tests` carries Microsoft's caveat that "manual review and code review are still required" ([Microsoft Learn](https://learn.microsoft.com/en-us/training/modules/develop-unit-tests-using-github-copilot-tools/3-generate-unit-tests-chat-view)), Postbot generates tests from observed responses that staff warn are "too static to test business logic" ([Postman community](https://community.postman.com/t/how-can-i-auto-generate-test-cases-from-a-postman-collection/78196)), Katalon StudioAssist turns a prompt into a script that writes a CSV ([Katalon](https://katalon.com/resources-center/blog/studioassist-data-driven-testing-ai-generated-test-cases)), and Qodo Cover was archived in June 2025 ([GitHub](https://github.com/qodo-ai/qodo-cover)). Diffblue's "20x" benchmark against Copilot is vendor-run with undisclosed methodology ([Diffblue](https://www.diffblue.com/resources/unit-test-generation-benchmark-diffblue-copilot-gpt5/)).

## Evidence converges on "LLM proposes, deterministic tools decide"

The research literature on LLM-generated inputs gives numbers precise enough to set policy. DiffSpec's best configuration produced **69.4% valid eBPF tests** — and only **24.8%** without human-written validity guidelines in the prompt — while a Fuzz4All baseline hallucinated opcodes or omitted `exit` in 61% of tests; because the model also produced wrong expected outputs, DiffSpec used differential execution across implementations instead of the LLM as oracle, and found 1,901 differentiating tests and four confirmed bugs where grammar fuzzing found four tests ([DiffSpec](https://arxiv.org/pdf/2410.04249)). Across 40 Python API methods and three frontier models, the best prompting produced property-based tests that were **both valid and sound only 41.74%** of the time, with generators that raised runtime errors and covered only ~21% of documented properties ([Proptest-AI](https://arxiv.org/pdf/2307.04346)). LlamaRestTest found a base Llama3-8B produced semantically valid REST parameter values **22.94–24.94%** of the time (0% on Spotify), rising to 72.44% after fine-tuning; crucially, its models are invoked only after repeated 4xx failures, with prompts that combine the parameter name, OpenAPI description and the server's error message — the LLM is used to find *valid* realistic values while invalid and edge inputs come from the search engine ([LlamaRestTest](https://arxiv.org/html/2501.08598v1)). Tanaka et al. observed the specific failure modes of LLM-written generators: over-constrained ranges (`n ≥ 1` in every test, missing the n ≤ 0 bug), string strategies that never produce the needed two-trailing-spaces input, and numeric ranges too small to expose precision bugs; their fix is to specify ranges explicitly (large inputs, 0, negatives, empty) and add 5–10 explicit boundary examples after the property run ([Tanaka et al.](https://arxiv.org/html/2510.25297v1)). The 2025 research roadmap states flatly that hallucination is "the major challenge of LLM-based testing" and that "there are no SOTA benchmarks in the test data and scenarios generation" ([Augusto et al.](https://arxiv.org/abs/2509.25043)).

Every strong result shares one architecture. Meta's ACH asked the model for artefacts a deterministic gate can accept or reject — builds, passes consistently, kills a mutant no existing test catches — leaving only relevance and style to human review; engineers accepted **140 of 191 (73%)** generated tests, and 49% of those "would have been discarded under a line-coverage criterion alone" ([Meta ACH](https://arxiv.org/html/2501.12862v1)). Qodo Cover operationalised the same gate in open source — coverage must increase, run five times to screen flakiness — before being archived ([Qodo Cover](https://github.com/qodo-ai/qodo-cover)). The Property-Generated Solver raised repair success from 46.6% with public tests alone to 75.9% by feeding back the shortest violating input, while noting that artefact accuracy fell from 82.4% on easy problems to 48.9% on hard ones ([PGS](https://arxiv.org/html/2506.18315v1)). Applitools' practitioner framing is the same: generative AI for creation and exploration, deterministic systems for execution and verification, "determinism at decision points" ([Applitools](https://applitools.com/blog/test-execution-generative-ai/)).

The closest precedent to cmtk is American Express's COBOL→Java validation, published July 2026. Deterministic "Witness Search" runs six algorithms (pairwise, three-way, Latin hypercube, adaptive random testing, MAP-Elites, UCB1) over input and stub state, executing every case on both systems; when search plateaus, an LLM proposes a "Mutation Skill" applied symmetrically to both programs and kept only if it adds branch coverage and passes the Parity Gate, which compares paragraphs entered, the ordered log of external operations and final observable values — "the LLM proposes, but deterministic tools decide". A 4,114-line production batch program reached **91.9% branch coverage and 166/166 parity** autonomously, but the authors state the limits plainly: "parity preserves bugs", it checks compatibility not correctness, and the gate misses intermediate state, floating-point rounding and exception types ([AmEx, arXiv 2607.28271](https://arxiv.org/pdf/2607.28271)). Their behavioural fingerprint — blocks entered, ordered side effects, final state — is a reusable definition of parity richer than response diffing, and it maps directly onto Zalando's per-endpoint thresholds and idempotency-only scope.

Reproducibility follows from the same evidence. Seeded determinism is near-universal within one library version — json-schema-faker's `seed`, faker's `seed()`, fast-check's seed and path, Bogus `UseSeed`, drizzle-seed, copycat — but no library guarantees it across upgrades: faker says so explicitly, Hypothesis warns its example database and `@reproduce_failure` blobs are "not stable across Hypothesis versions", Datafaker's `birthday()` shifts daily because it is relative to today ([fakerjs.dev](https://fakerjs.dev/guide/usage); [Hypothesis docs](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html); [datafaker issue](https://github.com/datafaker-net/datafaker/issues/1087)). The safe guarantee is artefact-level: generate once from a pinned recipe, hash and commit the artefact, and load the same bytes into both systems; dbt's seeds model this as version-controlled, code-reviewable CSVs, with the explicit warning that they are a poor fit for production data containing PII ([dbt docs](https://docs.getdbt.com/docs/build/seeds.md)). That warning has legal weight in the UK: the ICO's March 2025 guidance treats pseudonymised data (hashing, tokenisation, encryption) as still within UK GDPR's scope ([RPC on ICO guidance](https://www.rpclegal.com/snapshots/data-protection/summer-2025/ico-publishes-new-guidance-on-anonymisation-and-pseudonymisation/)), and the Ministry of Justice's rule is "By default, the MoJ does not permit testing using live data", with live data allowed by exception only after a DPIA ([MoJ](https://security-guidance.service.justice.gov.uk/using-live-data-for-testing-purposes)). A masked Jailer subset is therefore in-scope personal data; a synthetic set generated from DDL plus a seeded Faker is not.

## Design recommendation: /cmtk:data as a recipe compiler with gates

### Honest ceiling: three tiers of capability

The answer to "how good can it be" is tiered, and cmtk's documentation should say so. Tier one, where cmtk can be excellent and fully mechanical, is everything derivable from structure: valid, boundary and negative payloads from JSON Schema, OpenAPI, XSD (via translation), DDL and copybooks; FK-consistent, topologically ordered seed sets; CSV, xlsx, PDF, docx, fixed-width and multipart fixtures whose content is deterministic and whose bytes are deterministic where the format allows; and hostile-input corpora (BLNS, CSV injection, zip bombs, BOM/CRLF/encoding variants, 1900/1904 date serials, sign-nibble variants). Tier two, good only with additional inputs, is realism and relationships: value distributions, real max lengths and character sets need a masked production profile or a Jailer subset; cross-field invariants (`endDate >= startDate`, total = sum of lines) cannot be expressed in JSON Schema or XSD and must be hand-declared or mined from examples, tests and captured traffic; stateful sequences need OpenAPI links or traffic. Tier three, bounded by the oracle problem, is expected outputs and omissions: generic generators have no oracle beyond "must not 500", but cmtk's parity premise supplies a derived oracle — the legacy system — for every input it generates, which is why `/cmtk:data` should be understood as cmtk's *input* generator feeding `/cmtk:parity`, not as a standalone expected-output oracle. The benchmark figures set the realistic expectation that schema-synthesised data alone will plateau (no black-box fuzzer passes ~60% line coverage, and ~99% of specs disagree with their implementations), so captured traffic and spec examples are the primary corpus and synthesis is the supplement that reaches the boundaries traffic never hits.

### Pipeline and tool surface

The capability should run as a seven-stage pipeline exposed both as a plugin skill and as MCP tools, so it can run standalone from a runbook or requirements file as Sam wants, or as a stage of the full suite. **Inspect** reads the target — OpenAPI/JSON Schema, WSDL/XSD, DDL or a live SQL Server catalogue (FKs, check constraints, unique indexes, identity columns, computed columns, nullability, string widths), EF or C# model types, copybooks, sample traffic (HAR/VCR, MockServer captures), requirements or acceptance criteria text — and emits a target model that records, per field, which source justified each constraint. **Model** lets the LLM propose notional variables, partitions, state machines, business invariants and inter-parameter dependencies from code comments, docs and examples, each tagged "structure says / spec says / production says / history says" and each requiring human confirmation before it influences generation. **Plan** compiles a recipe: variables, partitions, 3-value boundaries, invalid partitions, constraint-aware pairwise strength, state-transition coverage level, oracle class per field, quotas, fixed seed, fixed clock, locale and generator versions. **Materialise** runs the recipe deterministically into artefacts — JSON request sets, topologically sorted SQL, CSV, xlsx, PDF, docx, fixed-width, multipart — plus a manifest. **Validate** re-parses every artefact (schema validation, FK resolution, round-trip decode of fixed-width and EDI, workbook and PDF re-read) and checks quotas. **Gate** rejects the set unless it is schema-valid, replay-stable across two runs, and — when the target code and a mutation or coverage tool are present — raises coverage or kills mutants versus the existing suite. **Load and compare** seeds both systems from the identical artefact and hands results to the parity comparison with semantic diffs. As MCP tools these are roughly `data_inspect`, `data_plan`, `data_materialise`, `data_validate`, `data_diff` and `data_load`; the plugin's SKILL.md should be when-invoked, not every-turn, since Anthropic's marketplace now surfaces per-plugin context cost ([Install and manage plugins](https://code.claude.com/docs/en/discover-plugins)), and the converged skills format means one SKILL.md plus scripts ports to Copilot with thin wrappers, as the existing copilot-modernization-port already does.

### Rules that keep generated data trustworthy

**Recipe over rows.** The committed artefact is the recipe plus a manifest, and rows are regenerated on demand; this addresses Bach's run-to-run variance without needing a deterministic LLM and matches the "review the harness, not every line" consensus. Because no published convention for recording seed and recipe provenance of AI-generated fixtures was found, cmtk should define one: seed, recipe hash, pinned generator versions, fixed clock, locale, input-source hashes, per-row technique and coverage item, per-field oracle class and justifying source, quota report and validation results. **Every row names its technique and coverage item** in 29119-4's chain, and rows are named by the condition they exercise (`qty_upper_bound_3bva`, `transition_cancel_from_shipped_invalid`) rather than by incidental content, which is Meszaros's role-naming applied to generated data. **Mandatory negative and boundary quotas**: the plan is rejected if more than a configured share of rows is happy-path, if any ordered field lacks 3-value BVA, if any field lacks an invalid partition, or if any state machine lacks one invalid transition per case — because the MutGen day=1 evidence shows coverage-prompted generation skips exactly these. **Constraint-aware combination** reads enums, FKs, check constraints and confirmed invariants and generates combinations with a covering array, so invalid cross-field combinations appear only as labelled negative cases, following NIST ACTS's constraint specification ([NIST](https://www.nist.gov/news-events/news/2010/11/Updated-nist-software-uses-combination-testing-catch-bugs-fast-and-easy)). **Separate "structure says" from "spec says" from "production says"**, and surface disagreements between them as findings rather than settling them, since Bolton's rule is that claims can be wrong and the tester's job is to expose the conflict. **Oracle tagging and escalation**: each expected value carries specified / derived / implicit / human; derived values come from the legacy system through the parity run; human-only rows go to SME review sized to the 50–100 golden records per entity, never auto-asserted. **Mutation delta, not coverage, is the self-check** where code is available, reported per row as killed or surviving mutants, with 100% coverage and a low mutation score flagged as a red flag. **Production-shaped, privacy-safe realism**: distributions, widths, character sets and outliers come from a masked profile or Jailer subset that is treated as in-scope personal data under the ICO's framing, while committed fixtures are synthetic from DDL plus seeded Faker with locale `en_GB` for UK estates; document metadata (`creator`, `lastModifiedBy`, PDF `Author`) is pinned to synthetic values so fixtures neither drift nor leak developer identities. **Minimal, self-describing fixtures**: per-test fresh data with load-bearing fields inline and filler behind named builders, never one seed database. **Time and identity under control**: dates relative to an injected clock, IDs allocated deterministically or marked non-comparable, collections sorted before comparison — the lesson of TMap's ageing dates and Zalando's non-comparable headers. **Parity scope and thresholds are explicit**: idempotent operations by default, per-operation match targets, discrepancy classes (new defect / legacy bug preserved / legacy bug fixed / non-comparable) persisted as data, and two distinct reconciliation tiers — full-population control totals and golden-record field comparison. **Small batches and loud uncertainty**: generate per seam or endpoint, mark low-confidence fields, and never present a plausible sample as evidence of coverage. **LLM-for-valid, engine-for-edges**: the model proposes realistic values only where the schema is silent (format-constrained fields, domain vocabularies) and is prompted with the parameter name, description and the server's rejection message as LlamaRestTest does; boundaries, negatives and combinations always come from the deterministic engine, and when coverage plateaus the model proposes a mutation that is kept only if the gate accepts it, exactly as AmEx did.

### First audience: .NET Framework to .NET 8 on SQL Server

For the launch audience the concrete path is: read the legacy SQL Server catalogue directly (constraints are the system of record; EF models on the new side are a cross-check, not the source), apply a virtual-FK configuration layer because legacy schemas frequently lack declared keys — every subsetter surveyed, from Tonic to Redgate to Greenmask, needed one ([Tonic subsetting](https://docs.tonic.ai/app/generation/subsetting/subsetting-about)) — and emit topologically sorted SQL with nullable-FK deferral in Jailer's style. Load the identical script into two Testcontainers.MsSql instances through `ExecScriptAsync`, one behind the legacy stack and one behind .NET 8, define the artefact against the legacy schema and derive the new-side load through cmtk's mapping step when schemas differ, and keep `HasData` only for static lookup tables that both systems share. Where realistic data is needed, Jailer's SQL Server subsetting feeds the profile, and the subset itself stays out of the repository. The recipe can optionally emit a Bogus `Faker<T>` with `UseSeed` for teams that want in-process .NET generation, but the parity guarantee rests on the materialised artefact, not on regenerating with the same seed on two runtimes whose package versions and cultures may differ. For WCF and ASMX contracts, the XSD translator plus `xs:pattern`-faithful string generation is the differentiator the Java tools lack. For batch interfaces, copybook-ts encodes cp037 records with the "file length is a multiple of record size" invariant as a cheap self-check, and the edge list is domain-specific: sign nibbles, `OCCURS DEPENDING ON` out of range, unsafe-integer money, RDW versus fixed. For documents the parity comparison converts rather than byte-compares — xlsx to per-sheet cell arrays diffed by business key with numeric epsilon and an explicit formula-versus-value choice, PDF to text per page with scrubbed dates and IDs, then raster with ignore rectangles — and multipart uploads are asserted on parsed parts (field names, filenames, content types, SHA-256), never raw bodies, since undici's boundary is random by design and Node 18.0–23.6 omitted the trailing CRLF ([undici formdata.js](https://raw.githubusercontent.com/nodejs/undici/main/lib/web/fetch/formdata.js); [philna.sh](https://philna.sh/blog/2025/01/14/troubles-with-multipart-form-data-fetch-node-js/)). The same pipeline serves any project because every stage keys off the target model rather than the source technology: a Postgres estate swaps the catalogue reader and gains Greenmask as the optional subsetter, a GraphQL API swaps the schema reader, and a Node service gains EvoMaster black-box as an external fuzzer.

## Conclusion

The decisive insight is that cmtk's parity-first premise turns the hardest problem in test-data generation — the oracle — into its strongest asset. Generic generators stop at "must not 500" or at human judgement of realism; cmtk already has a derived oracle for every input it can synthesise, which means `/cmtk:data` should be designed as a coverage-driven, recipe-emitting input generator whose success metric is not how many rows it produces but how many legacy-versus-new discrepancies per reviewed hour it surfaces, with each discrepancy classified and persisted. That reframing also bounds the LLM's role precisely: it proposes notional variables, invariants, realistic vocabulary and plateau-breaking mutations, and the deterministic engine, the schema validator, the mutation delta and the parity gate decide.

The second implication is competitive. The research found no open-source, permissively licensed tool that reads a target system and produces schema-aware, FK-consistent, deterministically seeded, negative-capable, document-aware test data with provenance — the only MCP that comes close charges for determinism, the best engine is Python-only, and the .NET and SQL Server world has nothing beyond schema-blind Bogus. Building that gap-filler for Node 22 with a recipe-and-manifest convention would give cmtk a capability no plugin marketplace currently offers, and because the manifest records technique, coverage item, source and oracle per row, it would also be the first generator a sceptical tester can audit in minutes rather than the 30–40 hours Bach needed for a demo.
